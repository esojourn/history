# 历史可视化网站 · 项目计划

> 状态：草案 v0.2（2026-11-20）　｜　三种展现形式的可交互示例见 [prototypes/index.html](../prototypes/index.html)　｜　待确认事项见 [第 9 节](#9-待确认的决定)

## 1. 目标与原始需求

做一个**直观展示各国历史**的网站。原始需求：

1. 支持多语言：先做中文，预留语言包翻译能力。
2. 先做中国历史：以朝代为主线，人物为节点，写清每个人物的年代、先后顺序与主要事件；人物之间的关联要直观地连线显示。
3. 覆盖其他主要文明；近代部分包含欧美、日本、韩国、东南亚各国等。
4. 古代史从圣经历史开始。

核心难点只有一个：**信息量极大，而屏幕很小**。下面所有设计都围绕"任何时刻只显示当前尺度下最重要的那一小部分"展开。

## 2. 展现形式：一条可缩放的"时间长河"

### 2.0 候选方案与示例

`prototypes/` 里用同一份示例数据（秦至西汉前期，28 人、14 件事、46 条关系）做了三种形式，每种都有桌面版和手机版，可以直接操作：

| 方案 | 一句话 | 最强 | 最弱 |
|---|---|---|---|
| **A 时间长河** | 横向时间轴 + 文明泳道，缩放时换一层内容 | 年代先后、多文明对照 | 上手要学缩放，制作量最大 |
| **B 历史长卷** | 像书一样纵向滚动，每个朝代一章 | 易读，手机体验最好，制作最简单 | 关系只是人名列表，不够直观 |
| **C 人物关系网** | 人物是点、关系是线的一张网 | 人物关系最直观 | 年代只有大致位置，放不下多文明 |

建议：**A 做主视图**；C 不单独成页，作为人物详情里"以他为中心的一圈关系"；B 的写法用于详情页和手机端的朝代页。本节以下内容按这个建议展开，待项目方看过示例后确认。

### 2.1 总体思路

主视图是一张**横向时间轴 + 纵向文明泳道**的大图，像地图一样可以拖动和缩放。缩放时不是简单放大，而是**换一层内容**（语义缩放）：

| 层级 | 屏幕跨度 | 显示什么 | 例子 |
|---|---|---|---|
| L0 世界 | 约 6000 年 | 各文明泳道、大时代色带 | 中国 / 圣经与以色列 / 近东 / 欧洲 … |
| L1 文明 | 约 1000–2000 年 | 朝代、政权色带，标志性事件 | 秦、汉、三国、晋 … |
| L2 朝代 | 约 100–300 年 | 人物**生卒条**、帝王在位条、事件点 | 刘邦、项羽、韩信；楚汉战争 |
| L3 人物 | 约 10–80 年 | 单个人物的生平事件、全部关系 | 韩信：登坛拜将 → 垓下 → 被杀 |

参考先例：Sebastian Adams 1871 年的《世界历史对照年表》（Synchronological Chart，正是从圣经纪年起笔）、Sparks 的 Histomap、微软 ChronoZoom。它们证明"泳道 + 时间轴"是承载通史最稳妥的骨架；我们在此基础上加上缩放、人物关系和多语言。

### 2.2 线框示意（L2：朝代层）

```
 时间 →     -230        -210        -190        -170        -150
          ┌───────┬──────────────────────────────────────────────
 朝代     │  秦   │                    西汉
          └───────┴──────────────────────────────────────────────
 帝王      秦始皇 ══╗二世   高祖 ═════╗惠帝═╗吕后══╗文帝 ═══════
 人物      项羽   ├────────────●┤
           刘邦  ├──────────────────────────┤
           韩信      ├─────────────────●┤          ● = 卒年/关键事件
           张良    ├──────────────────────────────┤
 事件               ▲陈胜吴广  ▲鸿门宴 ▲垓下之战   ▲白登之围
                    ╰──── 选中"韩信"后，连线亮起：刘邦(君臣) 项羽(敌对) 萧何(举荐) ────╯
```

- **人物 = 一根生卒条**，长度就是寿命，位置就是年代，先后顺序一目了然。
- **事件 = 时间轴上的点或短条**，与参与人物相连。
- **关系连线默认不显示**，选中或悬停某个人物时，才亮起他的关系线，其余内容变淡。这是避免"一团乱麻"的关键。

### 2.3 三个联动视图

| 视图 | 回答的问题 | 形式 |
|---|---|---|
| **时间长河**（主视图） | 谁在什么时候？谁先谁后？同一时期别处在发生什么？ | 泳道时间轴，语义缩放 |
| **关系图** | 这个人和谁有关系？是什么关系？ | 以所选人物为中心的 1–2 层关系网，连线按类型着色（亲属 / 君臣 / 师生 / 敌对 / 同盟 / 交游） |
| **详情页** | 这个人 / 朝代 / 事件的完整信息是什么？ | 独立网址的页面：简介、生平小时间轴、关系列表、相关事件、出处 |

三者共用同一份数据与同一个"当前选中对象"：在时间长河里点人物 → 侧栏出卡片 → 可展开关系图或进入详情页；在关系图里点另一个人 → 时间长河自动滑到他的年代。

### 2.4 控制信息量的五个手段

1. **语义缩放**：见 2.1，每层只显示该层的内容。
2. **重要度分级**：每个人物、事件带 1–5 级重要度，决定它在哪个缩放层开始出现（5 级在 L1 就可见，1 级只在 L3 可见）。
3. **选中聚焦**：关系线、次要标签只对当前选中对象显示。
4. **筛选**：按类别开关——政治、军事、思想文化、科技、宗教、经济。
5. **搜索直达**：输入"苏轼"直接飞到 1037–1101 年并选中。

### 2.5 多文明并列

- 每个文明一条泳道，可折叠、可调序。中国泳道内部遇到并立政权（三国、南北朝、五代十国、宋辽金夏）时，自动拆成子泳道。
- **同期对照线**：鼠标所在年份拉一条竖线贯穿所有泳道，直接读出"公元前 221 年秦统一六国时，罗马正处在第二次布匿战争（前 218 年爆发）的前夕"。
- **跨文明连线**：张骞通西域、鉴真东渡、蒙古西征、鸦片战争这类事件，作为跨泳道的连线呈现——这是多文明放在一张图上最有价值的地方。

- **展开与收起**（已在示例中验证，2026-11-20）：到了人物层，11 条泳道不可能同时摊开在一屏里。每条泳道有两种状态：
  - *收起*：只占一小条，色带那一行写最重要的大事，下面只留重要度 4 以上的人物（没有的话留最重要的一位）。
  - *展开*：按缩放程度显示全部人物，大事另起最多三行。
  - 默认只展开中国；点左栏的文明名称切换，另有“全部展开 / 全部收起”。
  - 选中某人时，与他相关的人即使在收起的泳道里也会浮出来，关系线可以跨泳道。
  - 页面比屏幕高时，年份刻度钉在顶上，拖动同时管左右和上下。
  - 秦汉这 120 多年、69 个人物的实测：默认状态约两屏高，全部展开约三屏高。

### 2.6 手机端

横向长图在手机上难用。手机端改为**纵向时间轴**（时间从上到下），一次只展示一条泳道，可左右滑动切换文明；关系图和详情页照常可用。选中某人时，其他文明里与他相关的人作为虚线框的“客人”排在右侧，点一下就切到那个文明。

## 3. 圣经历史与古代史的处理

需求是"古代历史从圣经历史开始"。落地时要解决一个实际问题：**圣经纪年、传统纪年与考古纪年并不总是一致**，中国上古史也有同样的问题（三皇五帝、夏代年代）。方案是不在数据里"选边"，而是把口径标清楚：

- 每个日期都带两项标注：
  - **纪年口径** `scheme`：如 `ussher`（乌雪纪年，创世于公元前 4004 年）、`lxx`（七十士译本纪年）、`xsz`（夏商周断代工程）、`scholarly`（学界通行）。同一事件可以同时记录多种口径下的年份。创世到巴别这一段是例外，见 3.1。
  - **确定度** `certainty`：`attested`（有同时代文献或考古互证）/ `traditional`（传统说法）/ `disputed`（有争议）/ `legendary`（传说）。
- 界面上用样式区分：确凿的画实线，传统说法画虚线，传说时代用淡色，并在图例里说明。
- **泳道安排**：古代部分第一条泳道为"圣经历史 / 以色列"（创世 → 洪水 → 巴别与列国 → 族长 → 出埃及 → 士师 → 王国 → 被掳与归回 → 新约时代），其下依次是两河、埃及、波斯、希腊、罗马，再接中国等。创世记第 10 章的"列国表"可作为从圣经泳道指向各文明泳道的连线。
- 从公元前 9 世纪起（亚述年表、米沙石碑等），圣经记载与外部史料大量互证，两套口径基本合流，之后不再需要区分。
- 中国史同理：公元前 841 年（共和元年）之后为确切纪年；之前的夏、商及五帝时期按上面的方式标注。

这样既能完整呈现圣经叙事，也不会和旁边泳道的年代互相打架，读者始终知道自己看到的是哪一种口径。

### 3.1 创世年代：只排先后，不标年份

项目方的立场：创世年代不能靠把家谱里的岁数简单相加得出；世界的年龄不是几十亿年，但也不会只有六千年那么近。据此：

- **太初部分（创世、洪水、巴别）不上刻度。** 在时间长河里，它画成圣经泳道最左端一段带斜线底纹的区域，标明"只排先后，不标年份"，内部事件只按顺序排列。
- **从亚伯拉罕起上刻度**，标为"传统说法、约数"；从王国时期起为确切纪年。
- 乌雪纪年（创世于前 4004 年）、七十士译本纪年（约前 5500 年）等推算，只在创世条目的详情里作为"历代推算"列出，不作为时间轴的依据。
- 圣经泳道标明"按圣经记载排列"。它与主流科学测年是不同的口径，不混在同一把尺上。

这一立场在解经传统里有依据，可称"家谱间隔说"：

- William Henry Green《Primeval Chronology》（Bibliotheca Sacra，1890）：创世记 5、11 章的家谱不是为推算年代而写，圣经家谱常省略世代（如马太福音第 1 章）。B. B. Warfield（1911）沿用此说。
- John Whitcomb 与 Henry Morris《The Genesis Flood》（1961）：在年轻地球的前提下承认家谱有间隔，把洪水与创世的年代前推数千年，同时反对无限拉长。William Barrick 等人的"有限间隔"说与此相近。（具体数字写进网站前要核对原书。）
- 对立意见：今天主要的年轻地球机构多坚持家谱无间隔、约六千年；Jeremy Sexton 等学者批评 Green 只证明了"可能省略世代"，没有证明"年数不可相加"。

## 4. 数据模型

原则：**结构数据与文字分离**。年份、关系、ID 与语言无关，只存一份；名称与描述按语言分文件。这是多语言能低成本扩展的前提。

### 4.1 实体

| 实体 | 说明 | 关键字段 |
|---|---|---|
| `polity` 政权/时代 | 文明 → 时代 → 朝代 → 政权，树状 | `id` `parent` `start` `end` `capital` `importance` |
| `person` 人物 | 节点 | `id` `birth` `death` `reign[]` `polity[]` `roles[]` `importance` `tags[]` |
| `event` 事件 | 点或时间段 | `id` `start` `end` `type` `participants[{person, role}]` `polity[]` `place` `importance` |
| `relation` 关系 | 人物之间的边 | `from` `to` `type` `start` `end` `source` |
| `place` 地点 | 第二阶段起用 | `id` `lat` `lng` |
| `source` 出处 | 每条数据可追溯 | `id` `title` `url` |

关系类型（初版）：亲属（父子、夫妻、兄弟、祖孙）、政治（君臣、继位、政敌、同盟）、学术（师生、同门、思想影响）、军事（对手、同袍）、交游（友人、唱和、举荐）。

### 4.2 日期

```yaml
birth:
  year: -230          # 天文纪年：公元前 231 年记为 -230（公元前 1 年 = 0），便于计算
  precision: year     # year | decade | century
  circa: true         # 是否为"约"
  certainty: disputed
  scheme: scholarly
  original: "秦王政十六年"   # 原始纪年写法，可选
```

内部一律用天文纪年整数，显示时再转换成"公元前 231 年"；避免"没有公元 0 年"带来的计算错误。

### 4.3 示例

```yaml
# data/person/han-xin.yaml          —— 结构，语言无关
id: han-xin
wikidata: Q…                        # 录入时查实并填写，用于日后自动拉取各语言译名
birth: { year: -230, circa: true, certainty: disputed }
death: { year: -195, certainty: attested }   # 公元前 196 年
polity: [western-han]
roles: [general]
importance: 4
```

```yaml
# locales/zh-CN/person/han-xin.yaml —— 文字，每种语言一份
name: 韩信
aliases: [淮阴侯]
summary: 西汉开国名将，"汉初三杰"之一。
```

```yaml
# data/relation/western-han.yaml
- { from: han-xin, to: liu-bang, type: minister-of, start: -205, end: -195 }
- { from: xiao-he, to: han-xin, type: recommended }
- { from: han-xin, to: xiang-yu, type: rival }
```

### 4.4 数据来源与质量

- **Wikidata / 维基百科**：生卒年、译名、基本关系；授权宽松（CC0 / CC BY-SA）。
- **CBDB 中国历代人物传记数据库**（哈佛）：数十万人物的亲属与社会关系，是"人物关联"最好的来源；其授权为 CC BY-NC-SA；本项目非商用，可以使用，但须署名，且由它衍生的数据要以相同方式授权。
- **中国历代纪元表**、二十四史：帝王年号与在位年代核对。
- 录入流程：AI 起草 → 人工核对 → 标记 `reviewed: true`。每条记录保留 `source`。构建时用校验脚本检查（卒年不早于生年、关系两端 ID 存在、人物年代落在所属政权范围内等）。

## 5. 多语言

- 界面文字：`locales/<语言>/ui.yaml`。
- 内容文字：`locales/<语言>/<实体类型>/<id>.yaml`，缺失时回退到中文并标注"未翻译"。
- 网址带语言前缀：`/zh/person/han-xin`、`/en/person/han-xin`。
- 每个实体挂 Wikidata 编号，新增语言时可批量拉取人名、地名的既有译名，只需人工翻译简介。
- 年代显示也走本地化：中文"公元前 221 年"，英文"221 BC"。

## 6. 技术方案（建议）

| 环节 | 选择 | 理由 |
|---|---|---|
| 站点 | **Astro** 静态站点 + 交互组件 | 内容即文件、无需后端；自带多语言路由与内容校验；详情页利于搜索引擎收录 |
| 时间长河 | **D3**（比例尺、缩放）+ Canvas 绘制 | 数千个对象仍然流畅，语义缩放完全可控 |
| 关系图 | D3 力导向或 Cytoscape.js | 成熟，支持按类型着色与布局 |
| 搜索 | Pagefind | 纯静态，支持中文分词 |
| 数据 | Git 仓库内的 YAML | 可审阅、可追溯、便于协作与翻译 |
| 部署 | 纯静态文件，放到已备案域名的主机上 | 构建产物不需要任何后端，能放静态文件的主机都行；线路与备案由项目方处理 |

字体与脚本全部本地托管，不依赖境外 CDN。

## 8. 路线图

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **P0 计划与原型** | 本文档定稿；数据格式定稿；用一小段样例数据做出可拖动缩放的时间长河原型 | 能在浏览器里缩放、点选人物、看到关系线 |
| **P1 中国史骨架** | 全部朝代与并立政权色带、历代帝王在位条 | L0–L1 层完整可用 |
| **P2 中国史纵深** | 先做一个"样板朝代"到 L3（建议秦至西汉前期：约 40 人、30 事件、80 条关系），验证形式后逐朝代铺开 | 样板朝代三种视图联动完整 |
| **P3 圣经历史与古代近东** | 圣经泳道、两河、埃及、波斯、希腊、罗马；纪年口径标注上线 | 同期对照线可跨泳道使用 |
| **P4 其他文明** | 日本、朝鲜半岛、欧洲各国、美国、东南亚、印度、伊斯兰世界 | 近代部分各国骨架齐备 |
| **P5 扩展** | 英文语言包；地图视图（疆域变迁）；手机端优化 | — |

顺序上先做 P0 原型再大量录数据：展现形式一旦调整，数据格式往往跟着变，先录后改代价很高。

## 9. 待确认的决定

1. **展现形式**：看过 `prototypes/` 的三种示例后，确认是否按"A 为主，B、C 各取一部分"来做，以及示例里哪些地方要改。
2. **样板朝代**：建议"秦至西汉前期"（故事性强、人物关系密、大众熟悉）；备选"三国"。
3. **亚伯拉罕之前是否完全不标年份**：3.1 的做法是只排先后。如果希望给一个大致范围（例如"一万至数万年前"），需要项目方给出说法。
4. **仓库公开还是私有**：以及数据是否打算开放授权。

已确定的事项（2026-11-20）：

- 项目**非商用**。
- **部署线路与备案由项目方处理**，已有备案域名。
- **技术方案由开发一方决定**，遇到需要取舍的地方再单独讨论。
- **纪年**：确切的和不确切的分开标注；创世年代不按家谱岁数累加，处理方式见 3.1。
